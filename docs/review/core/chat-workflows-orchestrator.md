## Strengths
- ChatHistoryStore is genuinely careful about concurrency: every RMW (including migration-on-read) holds a proper-lockfile lock with stale handling and bounded retries; tmp+rename atomic; corrupt files quarantined; capped at 500; mtime cache detects external writers (spec-covered).
- Workflow records deliberately minimal: terminal statuses strip testDraft/lastRepairedCode/lastRunResults; the spec asserts apiKey/conversationHistory never appear — conscious secret-minimization.
- Orchestrator resource discipline: synchronous busy-guard before the first await, all leases release in finally, browser lease force-closes on abort, lease release on failure spec-verified.
- Both durable writers use tmp+rename — mid-write crash can't tear the canonical file.
- Legacy chat migration is thorough (array and {role,content} shapes, stable synthetic ids) with good spec coverage.

## Test-coverage observations
- chat-history-store.spec: no corrupt-JSON quarantine test, no unrecognized-shape silent-wipe test, no 500-cap test, no cross-process lock test, no mtime-race test.
- workflow-store.spec: no corrupt-file/permission-error load test, no concurrent-update/lost-update test, no version-mismatch rejection; finalizeTerminal tested only for completed.
- continue-hitl-workflow.spec: no approve-when-file-deleted, no approve-vs-reject race, no test that rejects bypass the lease, no driveRepairLoop write-failure or null-update paths.
- Orchestrator has NO dedicated spec (flows.spec.ts tests cover/flows.ts); OPERATION_BUSY, browser-lease failure cleanup, abort force-close, trace end("aborted") untested.

## Verdict
**needs fixes** — the two HITL continuation races (stale-snapshot decision apply, deleted-file "completed") are realistic cross-process wrong-behavior paths, though nothing is blocker-level since both stores write atomically and chat RMWs are properly locked.
