# Core Review — site-discovery (root + detectors)

**Scope:** `libs/core/src/site-discovery/` root files + `detectors/` (19 source files, ~4.8k lines; crawler/ reviewed separately — see site-discovery-crawler.md)
**Method:** delegated line-by-line review (all files read fully; crawler/ helpers read only to verify call-site behavior; specs skimmed). Report-first — no changes made.

Clean categories: URL normalization logic itself is solid and excellently spec'd (fragment/query/index-file/trailing-slash covered); no cookie/token VALUES persisted to the knowledge base or logs (paths and counts only); coordinator.ts has no concurrency hazards; consistency.ts, discovery-error.ts, project-lock.ts, manual-handoff.ts, types.ts, index.ts — no findings.

## Strengths
- Blocker pipeline design: priority-ordered, first-match-wins, throwing detectors isolated with a warn, per-category skip memory surviving pause/resume via ignoredCategoriesJson.
- saveBlocker dedup semantics (update-in-place, re-open on re-detect, collapse legacy duplicates) carefully reasoned and precisely spec'd.
- failStaleSessions scopes its EXISTS to pages visited during THIS session with an explicit regression comment — crash-recovery subtlety that usually rots.
- looksLikeLoginUrl/looksLikeLogoutUrl path-anchored with documented OAuth-callback exclusions, single-sourced across crawler + handoff + CLI, with exemplary it.each matrices.
- Budget accounting: per-run committedUrls dedup plus a synchronous re-check before commit — maxPages can't be overshot under concurrency.

## Test-coverage observations
- loadSiteKnowledge has zero specs (knowledge-loader.spec only tests formatSiteKnowledge) — the DB-handle leak, resolved-blocker filtering, and MAX_ROUTES truncation untested.
- No end-to-end wall-clock cap test (only config resolution of maxRunTimeMs).
- No negative detector specs: password input on a non-login URL; captcha-iframe visibility; captcha-vs-auth ordering on a login page with reCAPTCHA.
- Budget exhaustion: no spec that maxPages leaves pendingRequests in a COMPLETED session, nor what --continue does then.
- Resume-failure recovery untested; preserveQueryParams changing between crawl and resume untested.
- No pagination tests for getPagesPaginated; savePage's INSERT OR REPLACE visit_count reset under the redirect race untested.
- DiscoveryQueryService has no direct specs; interstitial detection only tested with body-direct overlays.

## Verdict
**needs fixes** — two high-severity detector false positives (invisible captcha iframes pausing healthy sites; password fields on non-login pages dropping/misfiling pages) bite realistic crawls on first run, and the pause/resume state machine has two medium ways to strand a session unresumable; the data layer and URL logic are otherwise in good shape.
